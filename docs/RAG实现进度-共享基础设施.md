## 核心设计：怎么让FAQ和字幕两种数据"共存但不混"

Chroma只建了**一个**集合（`rag_documents`），不是给FAQ和字幕各建一个。区分靠每条记录
存的时候带一个`metadata = {"type": "faq"}`或`{"type": "subtitle", "video_id": ..., ...}`，
查的时候强制带上`where={"type": doc_type}`过滤条件，永远不会查到FAQ和字幕混在一起的结果。

字幕那边（项目二会用到）还能再叠加一层过滤——`extra_where={"video_id": "xxx"}"`，只在
同一个视频的字幕片段里检索，不会跨视频查到不相关的内容。代码实现是Chroma的`$and`语法：
```python
where = {"$and": [{"type": "subtitle"}, {"video_id": "xxx"}]}
```

## 为什么embedding模型换了（这个之前讨论过，这里正式定下来）

用的是`paraphrase-multilingual-MiniLM-L12-v2`，不是最开始方案文档草稿里写的
`all-MiniLM-L6-v2`——后者是纯英文优化的模型，网站是中/英/葡三语，需要模型本身对这
三种语言的语义理解都过关。

## embedding是怎么工作的（你要求理解原理，这里说清楚机制）

1. `SentenceTransformer`模型把一段文本变成一个384维的向量（一串384个浮点数），语义
   相近的句子，向量在空间里的位置也相近
2. `normalize_embeddings=True`把每个向量的长度统一缩放成1——这样比较两个向量"像不像"
   时，只需要算它们的点积（`dot product`），点积越大越相似，不用管原始文本长短造成
   向量长度不一样的干扰
3. Chroma负责把这些向量存起来、建索引，查询的时候拿"问题的向量"去跟"库里所有向量"
   比对，返回最相似的几个——这个过程就是"语义检索"，不是关键词匹配，问题和FAQ答案
   不需要用词完全一样，意思像就能匹配上

## 怎么验证的（实测，不是纸面设计）

写了一段测试脚本（没有留在代码库里，是临时跑的，验证完直接清理了测试数据）：

1. **embedding维度**：确认输出的是384维向量
2. **多语言语义相似度**（这个是重点，验证选这个模型是对的）：中文"免费用户每天能问几次
   问题" vs 英文"How many questions can a free user ask per day"（同一个意思，两种语言）
   → 相似度**0.888**；中文那句 vs 完全不相关的"今天天气怎么样" → 相似度**0.231**。
   数字差距很大，证明模型确实能跨语言识别语义相似度，不是瞎猜
3. **type过滤**：同时存1条FAQ数据+1条字幕数据，按`type="faq"`查询，确认只返回FAQ那条，
   字幕那条不会混进来
4. **video_id二次过滤**：按`type="subtitle"` + `video_id="test:video1"`查询，确认返回
   的记录里`start_time`字段是对的（12.5秒），证明时间戳信息完整保留、能查出来

## 一个顺带处理的问题：本地磁盘空间

空间，默认会把模型缓存下载到C盘的用户目录。已经把缓存文件夹整个搬到D盘，并设置了持久的
`HF_HOME`环境变量指向D盘——这是**本地开发机器**的环境配置问题，跟代码本身、跟Azure服务器
（Linux，没有这个问题）都无关，不需要写进代码仓库。
