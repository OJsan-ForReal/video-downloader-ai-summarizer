## 1. 分块策略（`_chunk_segments`）

```python
CHUNK_WINDOW_SECONDS = 30
```

字幕本身已经是segment（句子/短语）级别分好的，不按字符数切，只按**时间窗口合并相邻segment**
成chunk：从第一个segment开始累积，一旦当前segment的`start`比窗口起点晚了30秒以上，就把
累积的segment合并成一个chunk（文本用空格拼接、`start_time`取第一个segment的start、
`end_time`取最后一个segment的end），然后开一个新窗口继续累积。

**为什么是30秒**：文档里给的默认建议值，没有另外测过更优的数字。30秒对应的是"够不够
一段完整的话"的直觉——太短（比如5秒）容易把一句话切两半，检索出来的片段读起来没头没尾；
太长（比如2分钟）又会把好几个不相关的话题合并进一个chunk，检索命中了但里面大半内容跟
问题无关，稀释了真正相关的部分。先用这个值跑，后续如果发现问答效果不理想（比如经常引用
的时间点前后文缺失、或者检索到的内容答非所问），这是第一个可以调的参数。

**在哪里触发**：加在了`_save_segments`函数末尾（跟SQLite写入放在同一个函数里，不分散到
别处）——同一个视频不管走"平台字幕下载成功""Whisper转录兜底""B站CC字幕"哪条路径，最终都
会调用一次`_save_segments`，也就都会自动完成"分块+写入Chroma"这一步，不用在三处调用点
分别处理。

**旧数据清理**：`_save_segments`一开始就是"先删SQLite里这个video_id的旧行，再插入新的"，
这次照着同样的逻辑在Chroma那边也加了一句`rag.delete_by_where({"video_id": video_id})`，
删完再写入新chunk。这样"同一个视频被重新提取字幕"这个场景下，Chroma里不会残留旧内容
（验收标准3验证的就是这个）。

## 2. `CONTEXT_LIMIT_THRESHOLD`：定了多少、怎么定的

```python
CONTEXT_LIMIT_THRESHOLD = 12000  # 字符数
```

**沿用了原来`_build_chat_context_prompt`里一直在用的12000这个截断值，不是新拍的数字**。
这个值已经在生产环境用了很久——它对应的是当前`VideoSummarizer.FALLBACK_MODELS`这几个
免费模型实际能稳定处理的上下文量，并且留出了system prompt、多轮对话历史、模型回复这些
额外占用的空间。既然这个数字已经过实际使用验证是"能跑得动"的分界线，直接复用比凭空定一个
没测过的新数字更可靠。

**`token_count`选的是方案(a)：继续用字符数近似，没有引入分词器**。原因：这里只是一个
"字幕内容够不够短、能不能直接整段塞进prompt"的粗略判断，不是要精确裁剪到刚好塞满
context window——差个几百字符不会影响"走direct还是走rag"这个二选一的结果。中文场景
字符数和token数的换算关系确实不是严格线性的（一个汉字往往接近甚至超过1个token，比英文
单词的字符/token比例更"贵"），但项目目前没有任何tokenizer依赖，为了让这一个粗略判断
更精确专门引入一个新库，投入产出不成比例。如果之后发现这个阈值在中文长视频场景下经常
判断错（比如某些视频字符数刚好卡在12000附近、但实际token数已经超出模型窗口），是可以
后续优化的点，但现在没有实测数据支撑先不动。

**`RAG_TOP_K = 5`**：每个chunk覆盖约30秒内容，5个chunk合计覆盖约2.5分钟的字幕内容——
这个量级大致对应"一个问题通常牵扯的上下文范围"，取太少容易漏掉相关但排名稍低的片段，
取太多则会把不太相关的内容也塞进prompt，稀释掉真正命中的部分。跟阈值一样，这是可以
后续根据实际效果微调的参数。

## 3. 核心函数：`get_video_context`

```python
def get_video_context(video_id: str, question: str, full_text: str) -> tuple[str, str]:
    if len(full_text) <= CONTEXT_LIMIT_THRESHOLD:
        return full_text, "direct"
    results = rag.query(question, doc_type="subtitle", top_k=RAG_TOP_K, extra_where={"video_id": video_id})
    context = "\n".join(f"[{_format_ts(r['metadata']['start_time'])}] {r['text']}" for r in results)
    return context, "rag"
```

跟方案文档给的伪代码基本一致。返回`(context, mode)`，`mode`只是给调用方/测试观察走了
哪条分支用，`chat_stream`里直接把它丢弃（`_mode`变量名前缀下划线表示故意不用），不影响
prompt本身。

`chat_stream`签名新增了`video_id`参数，内部调用`get_video_context`拿到`context`后，
喂给`_build_chat_context_prompt`——这个函数原来做的`subtitle_text[:12000]`截断逻辑
删掉了，因为截断/检索的判断已经在`get_video_context`里做完了，`context`到这里已经是
处理好的最终内容。不管是direct分支返回的完整字幕、还是rag分支检索出的片段拼接，都保留
了`[mm:ss]`时间戳格式，这样system prompt那句"优先引用具体时间点"的指令，在两种模式下
都是有意义的。

## 4. `video_id`哪来的（这是本次改动里唯一超出"照抄伪代码"范围、需要单独说明的部分）

方案文档的伪代码里`get_video_context(video_id, ...)`直接假设`video_id`已经有了，但实际
接进`/api/chat`时发现：这个接口有一条"前端已经带着上次提取的`subtitle_text`过来，不用
重新提取字幕"的优化路径（省一次yt-dlp网络请求），这条路径下**原本压根不会计算`video_id`**。

而且要注意，`main.py`里已经有一个`video_id_for_url()`（来自`chat_history.py`，对URL做
SHA256哈希），但那是对话记忆模块自己的一套标识，跟字幕持久化/Chroma里存的`"平台:视频ID"`
格式的`video_id`是两套完全独立的东西，不能混用（用错了会导致RAG检索按错误的key过滤，
查不到任何chunk）。这次改动把原来main.py里唯一一个叫`video_id`的变量重命名成了
`history_video_id`，新增的字幕RAG用的量叫`subtitle_video_id`，避免以后有人看这段代码时
把两者搞混。

处理办法：在`SubtitleExtractor`上新增一个`get_video_id(url)`方法（逻辑跟`extract()`内部
算video_id的两行代码一样，只是抽出来单独可调用，没有改动`extract()`原有的计算逻辑，
风险最小）。`main.py`只在**真正需要**的时候才调用它：

- 前端没带缓存字幕 → 反正要整个`extract()`一遍，`video_id`跟着结果一起拿到，不需要
  额外调用
- 前端带了缓存字幕，但字符数**没**超过`CONTEXT_LIMIT_THRESHOLD` → 走direct分支根本
  用不到`video_id`，不调用（这是最常见的场景：短视频多轮追问，性能完全不受影响）
- 前端带了缓存字幕，且字符数超过阈值 → 这时候才调一次`get_video_id()`（一次yt-dlp视频
  信息查询，不下载字幕/不转录，比完整提取轻很多）

**已知的遗留成本，如实汇报**：长视频多轮追问场景下，上面第三种情况会导致每一轮追问都
重新查一次视频信息（因为前端目前只缓存了`subtitle_text`文本，没有把`video_id`也存起来
带回来）。这个请求很轻量，但确实是重复的。如果想完全消除，需要让前端把`video_id`也存进
它现有的字幕缓存状态里、`ChatRequest`加一个可选字段——这个改动不大，但涉及前端状态改动，
按之前文档里"前端集成先不做"的范围界定，这次没有顺手做，作为已知优化点汇报，需要的话
可以下一步做。

## 5. 为什么长视频不能跟短视频一样直接怼字幕（大白话版）

以前的做法是不管视频多长，都把字幕文本掐头去尾截到12000个字符，直接扔给AI。这在**短
视频**上没问题——字幕总共可能就3000字符，全塞进去AI能看到完整内容。但**长视频**（比如
两小时的课程，字幕全文可能有5万字符）就出问题了：截断只保留了前12000字符，也就是视频
**开头那一小段**，后面90%的内容AI压根看不到。这时候用户问一个关于视频后半段的问题，
AI要么瞎编，要么老实说"字幕里没有这段内容"——但其实内容是有的，只是被截断切掉了，AI
根本没看到。

RAG检索解决的就是这个"看不到"的问题：不再是"看前面一截、后面全部扔掉"，而是先把全文
按时间切成一个个30秒左右的片段（chunk），每个片段都提前转换成一个能表示"这段在说什么"
的向量存起来。用户提问的时候，把问题也转换成同样的向量，去跟所有片段的向量比对"哪些
片段的内容和这个问题最相关"，只挑最相关的几个片段（这里选了5个）喂给AI——不管这几个
片段是在视频的开头、中间还是结尾，只要内容相关就能被检索到。

这样做的代价是：如果用户问的问题比较宽泛（比如"这个视频讲了什么"），RAG可能挑不出
"最相关"的那几个片段，因为整个视频每部分都算相关，检索反而不如"看全文"准。所以文档里
明确要求**不是无脑全部走RAG**——短视频能完整塞进prompt的情况下，直接给AI看全文，
永远比"猜哪几段最相关"更可靠，只有当视频长到没法整段塞进去时，"检索出最相关的部分"
才是唯一可行的办法，属于"没有更好选择时的次优解"，不是比直接注入更好的方案。

## 验收标准逐条验证结果

用直接调用函数的方式验证（没有走真实yt-dlp/Whisper提取，用手工构造的假字幕数据模拟），
测完清理了所有`test:`开头的测试数据（SQLite和Chroma两边都清了，验证过`COUNT(*)`归零）：

1. **短字幕（60秒内容）走`get_video_context`，确认走的是"direct"分支**——PASS。
   构造了一个总字符数远小于12000的字幕，`get_video_context`返回`mode == "direct"`，
   且`context`就是原样的`full_text`，没有任何检索发生。

2. **长字幕（1小时内容，字符数超过`CONTEXT_LIMIT_THRESHOLD`）确认走"rag"分支，且返回
   内容带时间戳格式**——PASS。构造的字幕字符数超过阈值，`get_video_context`返回
   `mode == "rag"`，返回的`context`非空，且格式是`[mm:ss] 文本内容`。

3. **同一个`video_id`重新存字幕（模拟视频被重新提取），确认Chroma里旧chunk被清理、
   不会残留过期数据**——PASS。先存一版内容（含"训练技巧"关键词）并确认能检索到，
   再用完全不同的内容（含"完全不同的主题"关键词）重新调用`_save_segments`存同一个
   `video_id`，之后检索确认：旧关键词的内容不再出现在结果里，新关键词的内容能正常
   检索到。

4. **跨视频不会检索串——两个不同`video_id`各存一份字幕，只按其中一个`video_id`查询，
   确认结果里不会出现另一个视频的内容**——PASS。存了video_b（机器学习话题）和
   video_c（做饭话题）两份长字幕，按video_c的`video_id`过滤检索"红烧肉怎么做"，
   确认结果里没有混入video_b那边的任何内容。
